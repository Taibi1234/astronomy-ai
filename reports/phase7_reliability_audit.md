## 1. Finding R1 — the saved Phase 5 dataset leaks its labels (blocking decision)

### 1.1 What was observed

The repaired builder (A) runs and produces a dataset with the same 26 windows, the same 13/13 label
balance, and **identical** `segment_id`, `label`, `injected_depth_ppm`, `n_points`, and
`window_start_bkjd` for every window. But five flux-derived features differ for **8 of the 13 positive
windows**, and none of the negatives:

| row | segment | label | injected ppm | saved `depth_rel_ppm` | regenerated | ratio |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 1 | 300 | 605.6 | 266.3 | 2.27 |
| 3 | 4 | 1 | 300 | 386.1 | 166.2 | 2.32 |
| 5 | 6 | 1 | 75 | 180.1 | 97.6 | 1.85 |
| 7 | 8 | 1 | 300 | 640.9 | 302.2 | 2.12 |
| 13 | 14 | 1 | 225 | 422.9 | 175.5 | 2.41 |
| 17 | 20 | 1 | 150 | 338.5 | 170.4 | 1.99 |
| 19 | 22 | 1 | 150 | 353.5 | 185.2 | 1.91 |
| 21 | 24 | 1 | 75 | 301.1 | 216.1 | 1.39 |

The remaining 5 positives are identical because they contain no in-transit cadence, so injecting a
transit is a no-op there.

### 1.2 Cause — confirmed, not inferred

I recomputed the seven features twice for every window: once from the pre-injection detrended flux
(`win_flux_dt`, what the committed code uses) and once from the post-injection series (`synthetic`,
which the committed code computes and then never uses). For **all 26 windows** the saved values match the
post-injection computation to floating-point equality:

```
seg 0  label 1 | saved 605.64 | pre-injection 266.35 | post-injection 605.64  -> match
seg 8  label 1 | saved 640.92 | pre-injection 302.18 | post-injection 640.92  -> match
seg 20 label 1 | saved 338.51 | pre-injection 170.39 | post-injection 338.51  -> match
seg 1  label 0 | saved 232.70 | pre-injection 232.70 | post-injection 232.70  -> match (no-op)
```

So the frozen `reports/phase5_dataset.json` was generated by an earlier revision of the script that
computed features on `synthetic`. The committed script (and now the repaired one) computes them on
`win_flux_dt`; the `synthetic` variable is dead code, which is the fingerprint of that edit happening
after the artifact was written.

### 1.3 Why it matters

`depth_rel_ppm`, `contrast_ppm`, `mad_scatter`, `segment_std_ppm` and `mean_flux` all change when a
transit is injected. In the saved dataset those five features therefore encode the label. The Phase 5
metrics — F1 0.75, ROC-AUC 0.667, PR-AUC 0.771 — were measured on a dataset where the positive class is
partly readable from its own features. **They are inflated and should not be quoted as evidence of
classifier skill.** The Phase 5 audit's statement "no feature uses injected label or actual injected
depth directly" is true of the *code intent* but false of the *saved artifact*; the audit checked feature
definitions rather than recomputing values.

### 1.4 What I did and did not do

- **Did:** repair the builder so it implements the documented, leak-free logic; regeneration was written
  to `/tmp/p7_check` only; all comparison work is read-only.
- **Did not:** regenerate `reports/phase5_dataset.json`, re-run `phase5_features.py` /
  `phase5_baseline.py` on it, or touch `phase5_results.{md,json}`. The frozen artifacts are intact and
  hash-verified (§6).
- **Effect on the tests:** `tests/test_phase5_builder.py::test_saved_dataset_matches_repaired_builder` is a
  **strict `xfail`**. It asserts the desired property, currently fails because of R1, and will turn into
  an `XPASS` failure the moment the dataset is regenerated — which is the intended tripwire.

**Decision required:** regenerating the dataset fixes the leakage but changes the Phase 5 result. That is
a scientific change and is outside a "minimal reliability repair". Options:

1. Regenerate the dataset and re-run Phase 5, publish the corrected (lower) metrics with the old ones as
   a documented erratum. *Scientifically correct, most work.*
2. Keep the frozen metrics, publish them with an explicit leakage caveat (now in README §4 item 6).
   *Cheapest, honest, but a reviewer will find the caveat more interesting than the result.*
3. Drop the ML section from the portfolio and keep the transit pipeline. *Removes the defect from the
   narrative entirely.*

I recommend option 1 if the ML section is meant to demonstrate real skill, option 3 if it is not.

### 5.1 Call sites (exhaustive)

Grep across the whole tree (excluding `.venv/`, `HOME/`): **no definition of either name exists** in any
`.py`, `.md`, or `.json` file. They are referenced four times and defined zero times.

### 5.2 Intended semantics, as far as the code establishes them

Not invented — inferred from the surrounding code only:

- `blocks` comes from `contiguous_blocks(time)` (runs split at gaps > 1 h), then `merge_blocks(blocks, group)`
  for 1/2/4-orbit grouping. Each `b` is an index array into `resid`.
- `strat` is one quarter label per block, from `quarter_of(data["time"][b[0]], quarter_ranges)`.
- Return value is added directly to `model` (`y_star = model + shuffled`) and must therefore be a
  residual array the same length as `resid`.
- So both are block-resampling primitives producing a surrogate residual series: `moving_block_resid`
  draws contiguous blocks with replacement across the whole series; `stratified_block_resid` draws blocks
  within each quarter stratum. Any implementation would have to choose block-count, alignment and
  length-repair rules that the file does not specify.

### 5.3 Status and why I stopped

- **Incomplete.** The module implements block construction, fitting, diagnostics, plotting and reporting
  but is missing its two resampling primitives — the part that generates every number. It imports and
  lints; it cannot execute a single replicate.
- **Obsolete / superseded.** None of its declared outputs exist: `reports/results/phase4_statistical_validation.json`
  is absent, as are `phase4_residual_diagnostics.png`, `phase4_bootstrap.png`,
  `phase4_model_comparison.png`. The Phase 4 results that *are* committed come from
  `phase4_residual_diagnostics.py`, `phase4_block_bootstrap.py`, `phase4_injection_recovery.py`,
  `phase4_model_comparison.py`, and those were the ones audited in `reports/phase4_audit.md`.
- **Partially documented.** Its only external reference is
  `reports/phase4_statistical_validation.md` §7: "The existing `scripts/statistical_validation.py`
  produces `phase4_residual_diagnostics.png` when run fully" — a forward-looking statement, never
  satisfied.
- **Not a dependency of any committed result.** No committed JSON, figure, report table, or README
  headline number derives from it.

Per instruction I did **not** write the two helpers. Doing so would create a second statistical
implementation, risk a contradictory Phase 4 result set, and cannot reproduce an audited baseline
because none exists for it.

Options for the owner: (a) delete it as dead code; (b) add a deprecation header pointing at the
`phase4_*.py` chain; (c) reconstruct and re-run it as a *new*, separately reviewed analysis. I recommend
(b) — cheapest, keeps the provenance trail, changes no numbers.
